Milestone C - Minimal TCP engine                    -> DONE
  tcp <host> <port> [payload] does a full client TCP exchange against
  any reachable host: 3-way handshake (SYN -> SYN-ACK -> ACK), seq/ack
  tracking, checksums, an advertised window, a polled retransmit on no
  ACK (RTC 1s tick, Esc-cancelable), and a read-until-FIN accumulation
  of the response (up to TCP_PAYLOAD_MAX = 1024 bytes). Verified
  end-to-end in QEMU against Python's http.server: full 870-byte
  directory listing captured and printed, then clean close and back to
  the shell. (Retransmit is one-shot — enough for slirp, which ACKs the
  guest itself; a real RTO tick is still the honest long-term answer,
  but was dropped once the immediate correctness bugs were fixed.)
  Bug-fix history during bring-up: peer FIN was never ACKed (payload-0
  segments were skipped, so the server fast-retransmitted FIN forever
  and filled the RX ring); pure ACKs were being ACKed in return, echoing
  an empty ACK loop with a stale sequence; and nic_fetch_rx never cleared
  the RTL8139 descriptor's ROK bit, so once inbound traffic stopped a
  wrapped ring re-delivered the same frames forever (the guest's "infinite
  receive loop" — qemu itself never clears ROK for the driver).
  REAL HARDWARE: the RTL8168 backend (nic_driver_type 2) is the one that
  matters on desktop motherboards — it's the path DHCP/netinfo/dhcp
  diagnostics were exercised on. TCP rides the same driver-agnostic
  nic_send_ip/netpoll entry points, so it uses the RTL8168 descriptor
  ring unchanged. One real-hardware bug found in an audit: RxMaxSize was
  set to 0x1FFF (8191) while the RX buffers are 2048 bytes — a jumbo
  frame would DMA-truncate into the buffer but the descriptor length
  field reports the full size, so the RX copy would overrun. Fixed to
  0x0640 (1600, Linux r8169's MTU-1500 value). QEMU can't emulate the
  RTL8168, so the descriptor-ring RX/TX paths are validated by audit,
  not boot test.

Milestone C.1 - Real-hardware bring-up fixes          -> DONE, VERIFIED ON REAL HW
  Three real-hardware-only bugs found after C shipped (none of these show
  up under QEMU, which is exactly why they survived boot-testing there):

  1. Boot filesystem was pinned to device 0 (legacy ATA primary master).
     On real hardware with no PATA/IDE controller - a SATA-only board,
     which is most of them - device 0 never answers, so fs_load always
     fell through to "No disk detected - filesystem will not persist",
     even when ahci_init had already found and brought up the SATA disk
     as an AHCI port slot. Fixed: fs_load now falls back to scanning the
     AHCI slots ahci_init claimed at boot when device 0 doesn't respond
     (first pass for an existing SFFS volume, second pass for a blank
     disk to init fresh onto), and remembers which device actually holds
     the OS volume in a new boot_device variable. fs_save and cmd_format's
     "don't touch the boot drive" guard both use boot_device now instead
     of a hardcoded 0.
  2. e1000 NIC bring-up talks to its registers over MMIO (nic_mmio_base)
     through the kernel's cacheable identity map - AHCI's ABAR got the
     same treatment fixed early on (ahci_mark_uncached), but the e1000
     backend never got the equivalent call, so CTRL.RST and friends could
     read back stale cached values on real silicon instead of what the
     device just wrote. Fixed by reusing ahci_mark_uncached (it's generic
     - just clears caching on whichever identity-map page contains the
     physical address you hand it) on the e1000 BAR0 window right after
     it's read from PCI config space.
  3. RTL8168: a PHY bring-up routine (rtl_phy_power_up_and_renegotiate -
     select register page 0, clear the power-down bit, force BMCR
     reset+enable+restart-autonegotiation) was written but never actually
     called anywhere. The MAC-side soft reset only resets the MAC, not the
     PHY, so a PHY firmware left powered-down/not-negotiating meant
     RTL_IO_PHYSTATUS's link bit never asserted - .rtl_link_wait burned
     its ~5s budget and gave up, but nic_present still got set to 1
     regardless, so this failed silently: netinfo/dscan/etc. all looked
     fine, but every frame sent from then on was just dropped, and tcp
     (or anything else needing the network) hung until its own timeout.
     Fixed by wiring the call in right after the MAC reset completes, so
     autonegotiation runs concurrently with the rest of ring setup instead
     of starting cold right before the link-wait loop begins polling.
     (A fourth, earlier real-hardware RTL8168 bug - a posted-write-
     ordering issue where TX completion could be invisible to a plain RAM
     poll on this chip family - was already fixed before this pass, via a
     PCI-config-space read used as a completion barrier inside the TX wait
     loop. netdiag_dump_tx's diagnostics, still in the driver, were what
     surfaced it.)

  VERIFIED: tcp now works end-to-end on real hardware (RTL8168 chip,
  no legacy ATA - SATA SSD picked up via the AHCI fallback above).
  dhcp/netinfo were already confirmed working pre-fix; tcp was the one
  still failing (silent link-down, bug 3) until this pass.

Milestone D - HTTP take / give                       -> DONE
   take <url> <file> does an HTTP/1.0 GET, strips response headers
   (CRLF-CRLF scan), and writes the body to a local file via
   fs_write_file (SFFS v3 chained). give <url> <file> reads a local
   file, builds a POST with Content-Type and Content-Length headers,
   and prints the server's reply. Both parse http://host[:port]/path
   URLs, resolve via DNS, run the full TCP exchange (handshake +
   send + receive + FIN), and are Esc-cancelable. http_rx_buf is
   3072 bytes (bigger than TCP_PAYLOAD_MAX) to fit HTTP responses
   comfortably. Built on top of the tcp.asm engine unchanged.

   Assembled cleanly with nasm -f bin and the full image (build.sh)
   builds without error.

Final Plan: Multi-block files + networking + HTTP get/put (v0.2.0)
Milestone A — FS: multi-block (chained) files
Add node_next (word per node, 0xFFFF=end) to the in-memory table and the per-volume on-disk layout (content shifts +1 sector).
Version-aware format: superblock version 3 = chained layout; old version-2 volumes load/read fine (single-block), new features need a fresh fmt — no data loss on upgrade.
Chained content nodes get a new node_type (e.g. 3) so they're invisible to find_child/path walk but skipped by the allocator.
New helpers fs_file_len, fs_read_file, fs_write_extend (append a node to a chain); route existing view/show/lookfor/find/edit/owrite/del through them. Delete frees whole chains.
Cap: ~64 nodes/volume → files up to ~10 KB/volume (fine for text/config; note in README).
Test: big-file round-trip via get, then view/sync/reboot and verify.
Milestone B — NIC + base stack (netinfo / bounce / monitor / dns / net)
As planned: RTL8139 bring-up (PCI 10EC:8139, BAR0, polled RX/TX), Ethernet II + ARP + IPv4 checksum + ICMP echo + UDP + DNS client, same-subnet/gateway routing, static IP config (10.0.2.15/gw 10.0.2.2/dns 10.0.2.3), resb DMA buffers.
Test: netinfo, dns google.com, bounce 10.0.2.2, bounce 8.8.8.8, bounce google.com, monitor google.com (line per reply, Esc stops), unroutable → clean timeout. No-NIC regression.
Milestone C — Minimal TCP engine
Polled, no IRQs: 3-way handshake (SYN→SYN-ACK→ACK), seq/ack tracking, send/recv with a small advertised window, HTTP/1.0 + Connection: close so body = read-until-FIN (no chunked encoding).
Retransmit-on-no-ACK with a 1s-granularity RTO tick (RTC-based) — bounded, Esc-cancelable.
Test: raw TCP exchange against a host service via QEMU hostfwd.
Milestone D — HTTP get / put
URL parsing (http://host[:port]/path), DNS for hostname, connect, request build, response header parse.
get <url> <file> — streams body into a new multi-block file (via Milestone A writer), sync.
put <url> <file> — POST body = file content with Content-Length.
Test (QEMU): run a plain HTTP server on the host (e.g. Python http.server + a tiny POST endpoint), forward with -netdev user,id=n0,hostfwd=tcp::8080-:80; get http://10.0.2.2:80/... <file> and put a file back, verify contents. Also get of a >160 B file to prove chaining.
Budget & build
Bump KERNEL_SECTORS 260 → 290 (boot.asm:27) — the combined ~20-22 KB of new code won't otherwise fit. Still well below FS_LBA_START=300, and the 2 MB image has room.
NIC/DNS/TCP/HTTP buffers all resb (no file bytes); RX ring 8 KB, TCP recv ~2-4 KB, HTTP/tx scratch.
NASM flat-binary build unchanged; verify kernel.bin ≤ 290 sectors each milestone.
Honest risk notes
TCP is the hard part — minimal-but-correct retransmission/timing under polling. QEMU slirp terminates the guest's TCP (it ACKs the guest and relays), which is forgiving; real-hardware LAN servers are less so. Each milestone keeps it testable.
No TLS — plain HTTP only. On real hardware you'll point get/put at your own plain-HTTP server on the LAN. HTTPS sites (most public ones) won't work — that's a fundamental limit without a crypto stack.
RTL8139 is legacy; for modern real hardware a GbE driver (RTL8169/e1000e) remains a later milestone. [RESOLVED - see status update at top: e1000 and RTL8168 drivers both shipped alongside RTL8139.]
